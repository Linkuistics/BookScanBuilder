### F1 — High: the disposition grammar has no reason vocabulary or per-reason decision domain

**Evidence.** spec:91 accepts `--reason ID --decision reject|retain-unresolved`
and defines reject only for a suggestion: “Reject dismisses that assessment
suggestion; it does not clear the underlying unverified limitation”. The only
reason ID anywhere is the illustrative `skew-nonzero` (spec:119). Export needs
acknowledgement only for “retained unresolved reasons” (spec:207–209), and
spec:519–520 says an import-fidelity or extent concern “remains unresolved
unless explicitly disposed of”. Against that, k53 criterion 3
(`_baseline-review.md:33–34`) says “CropBox extent reasons remain unresolved
until k48's reviewed/restorable crop”, and spec:557–560 retains
orientation-unverified “until orientation is explicitly reviewed”, while this
handoff offers no orientation review (spec:74).

**Failure.** Nothing forbids `baseline disposition P --receipt R --reason
extent-change --decision reject`. The reason then leaves the summary's
unresolved roster and the acknowledgement-coverage set, and the export report
shows a rejected extent concern — contrary to k53 criterion 3. The same applies
to orientation-unverified (an orientation review recorded without its control),
an import-fidelity downsampling reason (a human dismissal reads as the fidelity
claim the design refuses to infer elsewhere) and unavailable-assessment
reasons. An implementer who forbids these has no spec basis and must invent the
error.

**Minimal remedy.** Add a version-1 reason table to the finite section: each
reason ID, its class (estimator suggestion versus limitation/concern) and the
finite decisions it admits — e.g. skew suggestion reject|retain-unresolved;
orientation-unverified, extent-change, import-fidelity and assessment-unavailable
retain-unresolved only in this handoff, or an explicit statement that a reject
stays in acknowledgement coverage and the report as unresolved. Name the code/
exit for a disallowed decision and reconcile spec:519–520 with k53's extent
rule. Checkable: reject on extent-change and orientation-unverified is refused
without a checkpoint; summary, acknowledgement scope and report still list both.

### F2 — Medium: global review revision makes each recorded action stale every outstanding receipt

**Evidence.** Review revision is project-wide and advances on every disposition
and inspection (spec:195–197). Receipts carry the displayed review revision
(spec:173–176) and are validated against the current one (spec:181–183); stale
packets must be refreshed (spec:127–130). Native receipts are per tile
(spec:92, example `receipts/native-001.json` at spec:121), one tile never
covers its neighbours (spec:131–132), and tiles are at most 768×768
(spec:154–155). k59 had to make the workflow “usable enough to agree, not merely
possible” (`05-DONE-design--baseline-delivery-k59.md:56`); the presented
trade-off shows one refresh after one disposition (spec:118–121).

**Failure.** Norwegian20's 3591×2695 baseline (spec:527–528) has 5×4 = 20 native
tiles. After inspecting all 20 at 1:1 the user records tile 1; tile 2's receipt
from the same packet is now stale (6). Recording all 20 needs 19 republished
page packets, each re-rendering the full comparison, 20×3 native panels and the
roster, and the receipt finally attested for tile k belongs to a refreshed
packet the user never looked at — pressure against “Never infer this act from
opening a file” (spec:92). An `--all` packet is unusable for a second action on
any page. The multiplicative consequence is not part of the presented trade-off.

**Minimal remedy.** Either (a) validate page receipts against what the action
depends on — the occurrence's image revision and a per-occurrence review-fact
revision — keeping global snapshot binding for summary receipts; or (b) let
`inspected` take a repeatable `--receipt` from one packet, recorded as one
atomic action at one displayed revision. Either changes an agreed public seam,
so confirm it with the human or state the per-action refresh cost explicitly in
spec/help. Checkable: all tiles of a 20-tile page recorded from one packet;
an intervening disposition on that occurrence still yields 6.

### F3 — Medium: “verified recovery” and the “recoverable predecessor” have no public operation

**Evidence.** Killed create: status “recommends a new unused directory or
verified recovery” (spec:239–240). INVALID_PROJECT remedy: “use named compatible
reader/verified recovery” (spec:306), inherited from the root (`_BRIEF.md:865–
866`). Upgrade “retains the recoverable predecessor” (spec:343–345). Yet the
command table (spec:86–94) has no recovery operation, and spec:879 says “No
unexposed recovery command or implicit reset is needed”. Help must give exact
remedies (spec:324–325).

**Failure.** One content-addressed asset is corrupted or deleted: every command
returns 3 directing the user to a recovery no command performs. The only
executable remedy is fresh import, discarding all dispositions, inspection and
acknowledgement records although earlier verified checkpoints are intact on
disk. An older reader meeting an upgraded project fails 3 with its predecessor
unreachable except by hand-editing the checkpoint pointer.

**Minimal remedy.** Either specify a finite operation (e.g. `bookscan baseline
recover PROJECT --checkpoint REV --workdir NEW` that verifies a named committed
checkpoint and copies it to a new unused project, leaving the damaged one
untouched) with errors and acceptance; or delete “verified recovery” and
“recoverable predecessor” from user remedies, say predecessor retention serves
only interrupted-upgrade resume, and state that recovery means fresh import with
review facts lost. Checkable: every remedy in help/JSON names an existing
command; corrupt-asset and killed-create cases exercise it.

### F4 — Low: replay precedence and receipt-integrity scope are not in the first-error order

**Evidence.** The durable retry record is checked before current-revision
validation (spec:215–222), but receipt verification is against the descriptor
“and the current revision” (spec:181–183), and the normative first-error order
(spec:312–314) puts “receipt validation” before “state/acknowledgement checks”
with no retry-lookup step. The workflow names Preview as the viewer (spec:104).

**Failure.** Implemented in listed order, an identical replay after later review
changes returns STALE_ACTION instead of its original result with replayed true.
After a committed action whose result was lost, Preview markup autosaved into
the packet PDF (or deleted view files) makes the replay INVALID_RECEIPT, and the
“refresh” remedy leads the user into a second, distinct action. Any markup
silently invalidates every receipt of that packet.

**Minimal remedy.** Insert the retry lookup explicitly: after the receipt file's
own authenticity (project ID, descriptor match), before currency and
packet-file integrity. State which packet files a receipt's validation reads,
and warn in help that viewer edits invalidate receipts. Checkable: replay after
a later change, and after view files are edited while the receipt JSON stays
intact, returns the original result; a new action from an edited packet is 6.

### F5 — Low: receipt-keyed retry makes receipts single-use without saying so

**Evidence.** “Reuse of its receipt with conflicting values … returns 6”
(spec:220–221). Several selection records may cover one snapshot (spec:204–
208, 93), acknowledgement changes no review revision (spec:198), so nothing
else makes the summary receipt stale; code 6's remedy is “refresh a packet/
summary, acknowledge exact current state” (spec:309).

**Failure.** Acknowledge pages 1–150 with `Export summary/receipt.json`, then the
rest with the same receipt: 6 with a stale-sounding remedy although nothing is
stale. The selection union is reachable only via one summary packet per
acknowledge command, which is undocumented.

**Minimal remedy.** State that a receipt authorises exactly one action request
and give the selection workflow (one summary per acknowledge command), with a
distinct code/remedy for a used receipt; or define conflict only for the same
request identity. Checkable: a two-command selection union case.

### F6 — Low: the report's `snapshot_id` is not reconciled with the new identities

**Evidence.** The report defines `snapshot_id` as “the exact acknowledged
accepted project revision” (spec:849), but the finite design now separates
image revision, review revision, export-snapshot digest (excluding the
acknowledgement) and checkpoint revision (advancing on it) (spec:192–199). The
acknowledgement object carries an “Exact snapshot ID” (spec:852), results carry
both `review_revision` and `snapshot_id` (spec:289–290), and existing report
meanings must be kept (spec:272).

**Failure.** An implementer writes the checkpoint revision — which differs from
the acknowledged value — or the review revision into a persistent public field
whose convention lasts in user PDFs; reports of one snapshot then disagree, or
fail to match the summary receipt's digest.

**Minimal remedy.** Define report `snapshot_id` and the acknowledgement object's
snapshot ID as the export-snapshot digest in the report table, and say whether
`review_revision` appears. Checkable: report, summary receipt and export result
carry one identical snapshot identity.

### F7 — Low: top-level JSON shape, `--help` with `--json` and result evolution are unspecified

**Evidence.** Finite stdout is exactly one `BookScanBuilderCommandResult` object
(spec:286–296); help takes precedence “at any level” and unknown subcommands exit
2 (spec:96–98). Preparation's unchanged records carry `schema_version: 1` but
no `schema` name (`src/bookscan/results.py:16–26`, `src/bookscan/prepare.py:74–
81`, `docs/specs/prepared-pdf.md:112–125`). Today `cli.py:85–89` treats any
`--help` token as precedence and prints human help even under `--json`, and
`cli.py:157–160` routes every non-prepare invocation into prepare's parser. The
additive-evolution rule (spec:377–381) sits in the action-envelope paragraph.

**Failure.** `bookscan --json bseline status P`, or pre-release `bookscan --json
process X --workdir Y`, has no defined record shape (prepare's unnamed v1 or
CommandResult v1). A note or viewer value equal to `--help` makes a mutating
command exit 0 with nothing recorded and non-JSON stdout. A later stage's new
code or status value has no stated v1 reader rule.

**Minimal remedy.** Specify that top-level, unknown-command and
COMMAND_UNAVAILABLE results are CommandResult v1 with `operation` null
(preparation's records stay distinguishable by the absent `schema`); define help
precedence as a standalone token not consumed as an option value, plus the
`--help --json` output; extend the evolution rule to CommandResult (closed
status set; additive codes only within existing exit classes; readers act on
exit class). Checkable: one acceptance case each.

### F8 — Low: ownership release and project identity omit the conditions that make them hold

**Evidence.** The nonblocking kernel lock keeps its pathname/inode, “canonical
project identity rejects aliased paths and replaced lock/store entries”, and
ownership is free after death and reap (spec:224–230). Acceptance signals and
kills only “the actual installed writer” (spec:443–447), while rendering and the
packaged helper run as native tools (spec:897, 907–908; `_BRIEF.md:831–841`).

**Failure.** With a process-associated POSIX record lock, closing any other
descriptor for the lock file (as a replaced-lock identity check might) silently
drops ownership mid-command. A renderer/helper child that inherits the lock
descriptor keeps ownership after the writer is killed and reaped, so the next
command is PROJECT_BUSY until the orphan exits — contrary to “clear on death/
reap”. Read literally, “rejects aliased paths” refuses a project addressed as
`/tmp/Book` (macOS `/tmp` → `/private/tmp`).

**Minimal remedy.** State required semantics without claiming a verified API: an
open-file-description lock on a descriptor no child inherits; children spawned
without it and terminated by the writer on caught signals; symlinked or
differently cased project arguments resolve to one accepted canonical identity,
while replaced internal lock/store entries are rejected. Checkable: kill the
writer while a renderer/helper child is live; open a project through a
symlinked parent.

### F9 — Low: the native 1:1 route names no mechanism and no consequence

**Evidence.** Packets give one PDF point per project pixel — 2×2 device pixels on
a 2× display, as spec:156–161 concedes — plus PNG tiles “for a viewer's actual
1:1 pixel mode”, with no viewer or PNG density named; the workflow names Preview
(spec:104). Native usability stays unfinished until demonstrated (spec:161–
163), and F retires only on complete delivery (spec:978–981).

**Failure.** If no ordinary viewer on this Mac shows the untagged PNG tiles at
one device pixel per project pixel, F's required native acceptance can never
pass, and the multi-session F owner has no designed exit except staying live.

**Minimal remedy.** Name the intended mechanism as a hypothesis F must verify
(e.g. PNG density metadata matching the display's backing scale, or a named
viewer setting) and the predeclared consequence of failure: a scoped boundary
question, never relabelling native inspection as pending or keeping F live
indefinitely.
