### F1 — High: `page-review-k47` is not one session, and its only fallback names itself

- **Where:** `.grove/39-impl--page-review-k47.md:29-79` (done-when) and `:84-87`
  (fallback: “decompose at a complete narrower orientation/review/resume/export
  handoff … no importer, schema, library, display or test-only child”).
- **Evidence:** the criteria bind, in one leaf: three-command CLI routing;
  full-MediaBox renderer with Rotate/UserUnit/box handling and effective-ppi
  assessment; a native Leptonica bridge and direct Pillow pin; a transactional
  content-addressed store, kernel writer lock and checkpoints; an authenticated
  Host/Origin/token server with Stop and signals; a browser roster/full/native
  reader with orientation controls; frozen export with report attachment;
  alias/no-clobber/writer-PID barrier tests; a test-owned browser driver and a
  denied-read boundary; six fixed cases with resource costs. This repo already
  measured the same failure on a strictly smaller subsystem: `prepared-pdf-k13`
  (`.grove/12-k13/`) exceeded one session and was cut into `prepared-preview-k16`
  and `prepared-pdf-k17`; the product it produced is 1,475 lines
  (`src/bookscan/*.py`) with no server, store, UI or sampler. The other three
  charters each name a concrete narrower handoff (`40-impl--rigid-pages-k48.md:68-71`,
  `41-impl--spread-pages-k49.md:63-66`, `42-impl--book-placement-k50.md:77-80`);
  k47's sentence is circular because the “complete narrower orientation/review/
  resume/export handoff” is k47 itself and the root forbids the horizontal cuts
  (`_BRIEF.md:673-677`).
- **Consequence:** the first and most load-bearing slice will outgrow its session
  with no pre-agreed vertical cut, so the implementer must invent one under
  pressure (or ship the horizontal split the root forbids). The risk lands on
  the foundation every later stage extends.
- **Remedy (checkable):** name the narrower complete handoff in k47's own text.
  One candidate that respects the vertical rule: stage A = import, snapshot,
  assessment, any-page full/native reader, project resume, Stop/signals and
  acknowledged export of unchanged baselines (no accepted-revision state); stage
  B introduces the accepted-revision state with exact orientation preview/accept/
  discard/revert in its controls, resume and export. State which dependencies
  (Leptonica bridge, Pillow pin, F5's analyzer) ride with which stage; the
  estimator's only k47 consumer is advisory triage, so it may move to k48.

### F3 — Medium: the representation-policy remedy is scheduled after three stages that build on it

- **Where:** `_BRIEF.md:791-800` (a technical stage may retire with verified
  >300-ppi losses; “hand a precise remedy/representation-policy question to k28”),
  `_BRIEF.md:802-806`, `.grove/44-planning--corrected-book-k28.md:36-48`;
  `40-impl--rigid-pages-k48.md:55-57` (“Source-resolution/colour loss stays failed
  preservation”).
- **Evidence:** the fixed 300-dpi RGB baseline is the substrate of k48's sampler,
  k49's regions and k50's placement (assets, mappings, report fields, fixtures).
  k28 runs after k48, k49, k50 and k27, so a representation change decided there
  re-derives all three. Two further ambiguities: the root classifies only
  “>300-ppi” loss as a signed limitation while k48 says “resolution/colour loss”,
  so a fixable renderer colour-conversion defect can be read as a retirable
  numerical fail; and no fixed case is known to exceed 300 ppi
  (`docs/research/scan-geometry-a.md:33-35`: 150, 220, 300 ppi), so the failure
  path is exercised only synthetically in k47.
- **Consequence:** the single decision most likely to invalidate later work has
  no gate before the dependents start, and a real defect can be relabelled a
  handed-forward limitation.
- **Remedy:** make k47's retirement name, per fixed case, whether the baseline's
  fidelity is `passed`, `failed: signed >300-ppi limitation` or `failed: defect`
  (the last blocks retirement per `_BRIEF.md:793-795`); and require that any
  verified `failed: signed limitation` on a fixed case put the policy question
  live **before k48**, not only before k22/k23. Align k48:55-57 to the root's
  “>300-ppi” wording or define colour loss separately.

### F4 — Medium: no pass condition for ≤300-ppi native fidelity, and the detector keys only on >300 ppi

- **Where:** `docs/specs/rotation-processor.md:74-79` (reason added only for
  “effective ppi above 300, or unavailable”), `:514` (the seam: >300-ppi,
  one-bit, grayscale fixtures; “a known erased fine feature must fail”),
  `39-impl--page-review-k47.md:58-61, 69-71`.
- **Evidence:** the six fixed cases are ≈300 ppi or below
  (`scan-geometry-a.md:33-35`; `prepared-pdf-copy.md:55-59` shows 2480×3505 and
  3509×2480 A4 at 300 ppi), so none triggers the >300 reason; Algorithm Design20's
  one-bit JBIG2 is rendered into an RGB raster whose pixel phase and filtering are
  Poppler's. The charters state wrong-subject controls (erased feature fails) but
  not what comparator and tolerance make an *unedited* ≤300-ppi fixed case
  `passed` rather than `unavailable`.
- **Consequence:** “Algorithm Design20 unchanged preservation” has no stated
  independent pass rule; the likely outcomes are an unspecified comparator that
  the baseline's own renderer satisfies by construction (the exact “passed from
  baseline bytes” the plan forbids) or a permanently `unavailable` result.
- **Remedy:** k47 states, before outputs, the independent source-native
  comparator (native image objects mapped through their placement, not a second
  render by the same renderer), its tolerance justification, and the pass/fail/
  unavailable rule for ≤300-ppi pages, including one-bit-to-RGB grid effects.
